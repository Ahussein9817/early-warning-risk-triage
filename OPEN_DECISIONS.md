# Open Decisions, read before directing the agent in Claude Code

**Status as of 2026-08-22:** three of the original three decisions are resolved (embedding model, deployment target, build mode), plus a fourth that emerged mid-build (hand-labeled sample size). One concrete item remains: the HuggingFace Space itself hasn't been created/pushed yet, see item 2.

1. **Embedding model (Requirements section), RESOLVED.** `sentence-transformers/all-MiniLM-L6-v2` (384-dim, ~80MB), chosen for fast CPU inference and small footprint over `all-mpnet-base-v2` (slower, larger) and `BAAI/bge-small-en-v1.5` (needs a query-instruction prefix). Confirmed finalized and documented in both `BUILD_INSTRUCTIONS.md` Requirements and `README.md` Methodology → Text embeddings, not left unstated.

2. **Streamlit deployment target, decision RESOLVED, execution NOT DONE.** Target chosen: **HuggingFace Spaces**, GitHub-synced (this repo's `README.md` carries the Space YAML frontmatter, `app_file: dashboard/app.py`) rather than a second, separately-maintained repo. This is documented in `BUILD_INSTRUCTIONS.md` Requirements and `README.md`'s Dashboard section.
   - **What's actually still open: the public Space doesn't exist yet.** No GitHub repo has been pushed, no HuggingFace Space has been created. `project_description.md` promises "a deployed Streamlit dashboard," and right now the dashboard only runs locally (verified working, screenshots/live-testing done in-session), a local-only dashboard does not satisfy that deliverable. **This is the one concrete thing left before the project can be called finished**, and it needs your GitHub/HuggingFace accounts, not something the agent can complete unilaterally. When ready: `git init` + push to GitHub, then create an HF Space (Streamlit SDK) linked to that repo.

3. **~~Full implementation vs. scaffold~~, RESOLVED (revised): full implementation, narrated checkpoint per section.** First landed on scaffold-first pair-implementation (builder writes the code, agent reviews); revised after the builder decided they'd rather observe and be walked through the work than write it themselves given their inexperience. Trade being made deliberately: this builds the ability to read, explain, and direct the pipeline, not the ability to independently write one like it from scratch later. Claude Code now builds each section fully, then must walk through the actual code with the builder: what it does, why, and tradeoffs, before moving to the next section. No section proceeds without the builder reviewing and approving the walkthrough. Held for the entire build, Sections 1-7, with no further changes.

4. **Hand-labeled evaluation sample size, RESOLVED (emerged during Section 6, not in the original three).** Spec called for 100-200 rows. A 150-row template was generated (`src/sample_for_labeling.py`, seeded random sample from the model's test split, excluding `company_response`/`timely`/the proxy label to keep the labeler's judgment independent). 106 of the 150 were actually hand-labeled, within the 100-200 range, so usable as-is; the remaining 44 were never filled in and evaluation proceeded on 106. A follow-up consistency-recheck pass (19 rows, 18 corrected) fixed a labeling inconsistency between `"Debt is not yours"` and `"Debt was result of identity theft"` sub_issues, documented in `BUILD_INSTRUCTIONS.md` Inputs and `README.md` Methodology, not silently corrected.

## Reminders from the source material, for when you're actually running the cycle in Claude Code

- Only interact with the agent through the spec, don't give it verbal patches that don't make it back into `BUILD_INSTRUCTIONS.md`. If a fix works, write it into the spec so the next run reproduces it.
- "The agent wrote it, so it's right" is the first trap. Spot-check baseline vs. fused predictions against the actual narrative text by hand before trusting `comparison_report.md`.
- "It worked on the sample" is the third trap. CFPB narratives are messy, test the empty-narrative path and a malformed-record path explicitly, not just the happy path.
